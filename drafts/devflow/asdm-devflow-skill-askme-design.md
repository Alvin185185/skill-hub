## 1. 文档定位

本文件是一份独立自洽的需求访谈设计，目标是把"想做一个研发流程 Skill"的模糊想法，澄清成可进入总体设计的完整输入。

1. 信息来源有三类：用户输入、仓库现状、既有设计稿。第三类只提供候选素材，其结论在本文件中一律是待评估的候选方案，不是事实；
2. 从既有设计稿吸收的内容已归化为本文件自己的背景与候选方案，可独立阅读，无需跳转任何外部文档，也不依赖其编号体系；
3. 将需求拆成可单独确认的原子决策点和子项，为每个提供背景、候选方案、推荐答案、理由、代价、验收标准和下游影响；
4. 通过用户回答检查候选方案的遗漏、冲突、过度设计和不合理前提；
5. 只把用户明确确认或明确标记为不适用的内容交给总体设计。

推荐不等于确认。"按你建议""都可以""你决定"不等于确认，必须复述具体方案和影响，请用户明确接受或修改。

## 2. AskMe 的目标和边界

### 2.1 AskMe 必须解决的问题

AskMe 要把"想做一个研发流程 Skill"的模糊想法，澄清成可进入总体设计的完整输入，至少覆盖：

- Skill 解决的问题、用户、场景、成功结果和非目标；
- Project、Feature 或其他工作对象及其身份关系；
- 生命周期、阶段、命令、分支、门禁、暂停、恢复和失败处理；
- 文档、状态、配置、代码、测试、运行时和证据等产物；
- AI、子 Agent、用户和真人裁决者的职责边界；
- 变更、修正、影响分析、审批、传播和回滚；
- UI、外部集成、权限、数据迁移、安全和其他高风险能力；
- Skill 的目录、协议、测试、加载、打包、发布和最低可交付范围。

### 2.2 AskMe 不直接完成的事情

- 不在 AskMe 阶段完成总体架构、字段级 API、组件树或代码实现；
- 不把推荐方案直接写成已确认基线；
- 不因为既有设计稿已有结论而跳过确认；
- 不把实现细节全部变成必须阻塞用户的长问卷；
- 不在关键目标、范围、流程或质量规则尚未确认时进入总体设计。

实现细节仍要登记。它们可以被标记为"推荐默认值""条件问题"或"详细设计阶段确认"（统一登记于延迟确认清单），但不能因为暂不阻塞 AskMe 就从设计地图中消失。

## 3. 事实、假设和推荐的分离

### 3.1 输入分类

| 类型 | 含义 | AskMe 处理 |
|---|---|---|
| `known` | 用户明确说过，或仓库/配置可以验证 | 作为背景事实，附来源 |
| `unknown` | 尚未确认，且会影响设计 | 必须登记为决策点或条件问题 |
| `assumption` | 为展示方案临时采用的推断 | 单独列出，不得进入基线 |
| `recommendation` | Skill 根据事实提出的候选方案 | 提供理由和代价，等待用户接受/修改/拒绝 |
| `confirmed` | 用户明确选择、接受或补充 | 才能进入总体设计输入 |
| `not_applicable` | 用户明确确认该能力不适用 | 记录理由和关闭范围 |
| `blocked` | 需要外部事实或用户裁决才能继续 | 记录阻塞原因和恢复动作 |
| `conflict` | 不同来源或已确认结论相互矛盾 | 暂停依赖它的下游问题，先裁决 |

### 3.2 推荐答案的规则

推荐答案至少要说明：

- 推荐采用什么具体方案；
- 推荐解决哪个已知问题；
- 相对其他方案的收益和代价；
- 哪些条件成立时推荐会改变；
- 对命令、状态、产物、实现复杂度和后续维护的影响。

"按你建议""都可以""你决定"不等于确认。AskMe 必须复述具体方案和影响，请用户明确接受或修改。

## 4. 决策顺序和依赖原则

决策点按以下依赖顺序展开。后面的决策不能在前置决策仍为 `unknown`、`blocked` 或 `conflict` 时强行关闭。

```text
目标与边界
  ↓
用户与场景
  ↓
工作对象与身份
  ↓
范围、生命周期和流程骨架
  ↓
命令集合与命令契约
  ↓
状态、配置、文档和产物
  ↓
调研、证据、任务和执行
  ↓
Review、质量门禁和收敛
  ↓
变更、修正和同步
  ↓
UI、外部集成、高风险和流程档位
  ↓
Skill 开发、测试、加载、打包和发布
  ↓
完整性自检与总体设计交接
```

条件问题只有在触发条件确认后展开。例如：

- 只有确认"Skill 实际修改代码"后，才展开 Worker、Verifier、权限和运行时问题；
- 只有确认"涉及 UI"后，才展开 SVG、style token、截图、可访问性和视觉一致性；
- 只有确认"需要变更传播"后，才展开 proposal、impact、archive 和影响链；
- 只有确认"存在 Project/Feature"后，才展开父子对象、MVP 和 foundation_ready。

### 决策点 D-A1：Skill 的首要问题

**问题**：Skill 首先要解决什么问题？

**背景**：候选素材把问题归纳为"只补文档完整性"还是"覆盖全流程闭环"之争：只在需求/设计环节做增强，执行、验收、同步问题会留在流程外部；覆盖需求、设计、拆解、执行、质量和变更全闭环，才能验证设计真正被执行，但 Skill 复杂、实现周期长。

**前置依赖**：无（首个决策点）。

**已知事实**：用户已在前序轮次给出结论（见"用户结论"）。

**未知影响**：不确认则所有后续命令、质量门禁、实现优先级和最低交付范围均无基准。

**候选方案**：

| 方案 | 内容 | 优点 | 代价 |
|---|---|---|---|
| A | 只补需求和设计完整性 | 范围小、容易落地 | 执行、验收、同步问题留在外部 |
| B | 覆盖需求、设计、拆解、执行、质量和变更闭环 | 能验证设计真正被执行 | Skill 复杂、实现周期长 |
| C | 先解决用户指定的一组缺口 | 便于快速验证 | 可能形成不完整流程 |

**推荐答案**：以 B 为目标，但分三期实现；第一期先保证状态、路由、执行验证、证据和恢复闭环。

**推荐理由**：只有 B 能形成"设计被真正执行"的验证闭环；分期降低一次性实现风险。若用户实际只需要文档增强（纯设计阶段工具），推荐改为 A。

**用户结论**：同意方案 B。Skill 的目标覆盖需求、设计、拆解、执行、质量和变更闭环；第一版先实现状态、路由、执行验证、证据和恢复闭环，其余能力后续分期实现。除上述分期边界外，本次未额外确认明确排除项；其他候选问题是否纳入及其优先级由 D-A2~D-A11 继续确认。（2026-08-25 确认；表述按 5.0 归化，语义不变）

**状态**：✅ 已确认（`confirmed`）

**验收标准**：能够逐条说明纳入的问题、对应能力、完成证据和不纳入的缺口。

**下游影响**：决定所有后续命令、质量门禁、实现优先级和最低交付范围（D-A2~D-A11、D-L4）。

### 决策点 D-A2：拆解任务的执行编排缺失

**问题**：拆解生成任务后，Skill 是否在用户显式调用 `execute` 后，负责按依赖选择并编排执行这些任务？

**背景**：当前拆解阶段能够生成任务和验证步骤，但后续没有机制在用户审核并显式调用 `execute` 后，按计划选择可执行任务并交给 Agent/Worker 实施，也没有统一的构建、启动和运行记录。因此，计划可能已经生成，却没有真正进入执行阶段。这里的执行编排不等于拆解完成后自动开工：用户仍需先审核需求、设计和任务计划。

**前置依赖**：D-A1。

**已知事实**：D-A1 已确认第一期包含状态、路由、执行验证、证据和恢复闭环；本项只确认其中的任务执行编排能力。

**未知影响**：不确认则拆解产物无人消费，任务状态无法从计划进入实施，执行与恢复链路没有入口。

**候选方案**：

| 处置 | 内容 | 优点 | 代价 |
|---|---|---|---|
| 保留-第一期 | 纳入第一期执行编排；拆解完成后等待用户审核，用户显式调用 `execute` 才启动 | 第一期可以消费拆解任务并建立受人工门禁控制的实施入口 | 需要调度、Agent/Worker、构建和运行记录能力 |
| 保留-后续期 | 纳入第二/三期 | 第一期开工较快 | 与 D-A1 已确认的第一期范围不一致，需显式修订 D-A1 |
| 修改后保留 | 只做任务选择和派发，执行由用户完成 | Skill 实现量较小 | 任务执行状态和失败恢复仍可能脱离流程 |
| 延后 | 待条件明确再裁决 | 暂时不增加执行复杂度 | 拆解产物继续停留在计划层，闭环无法运行 |
| 删除 | 不由 Skill 编排执行 | 范围最小 | D-E6 与 D-H 执行链路失去前提 |

**推荐答案**：保留，第一期。

**推荐理由**：没有任务执行编排，拆解只能产生静态计划，D-A1 确认的执行验证闭环无法启动。第一期先建立执行入口，但执行入口必须由用户显式调用 `execute` 打开，以便人在实施前审核文档和任务拆解；启动后按单任务执行，完成一个任务即暂停等待确认，后续验证能力才能消费实际执行结果。

**用户结论**：采纳“保留-第一期”，但采用人工触发：拆解完成后先进入待审核/待执行状态，不自动开工；用户显式调用 `execute` 后，Skill 才按依赖选择并派发任务。每个任务完成并记录验证结果后暂停，用户确认后再继续下一个任务。（2026-08-26 确认）

**状态**：✅ 已确认（`confirmed`）

**验收标准**：拆解完成后处于待审核/待执行状态，不得自动派发；用户显式调用 `execute` 后，能按依赖选择可执行任务，创建对应执行记录并交给 Agent/Worker 实施；每个任务完成后暂停并留下用户确认记录；构建或运行失败有明确状态和恢复入口，执行结果交给后续验证环节。

**下游影响**：D-E6、D-H3、D-H4、D-H5、D-H6、D-H7；D-L4 执行编排与运行时相关能力分期。

### 决策点 D-A3：执行结果的验收验证缺失

**问题**：任务执行后，Skill 是否负责按 DoD 和验证步骤逐条验证结果，并保存独立验收证据？

**背景**：即使任务已经执行完成，如果没有按 DoD 和验证步骤实际检查，流程仍只能证明“代码被改过”，不能证明“需求已满足”。当前进度检查主要做事后标准对照，缺少逐条命令执行、预期比对、独立验收和证据留存。

**前置依赖**：D-A1、D-A2。

**已知事实**：D-A1 已确认第一期包含执行验证和证据闭环；D-A2 负责提供可被验证的实际执行结果。

**未知影响**：不确认则任务可能在没有需求级验证和证据的情况下被标记完成，无法证明设计真正被执行。

**候选方案**：

| 处置 | 内容 | 优点 | 代价 |
|---|---|---|---|
| 保留-第一期 | 纳入第一期验证与验收 | 第一时间建立需求到证据的闭环 | 需要验证命令执行、断言比对和独立 Verifier |
| 保留-后续期 | 纳入第二/三期 | 第一期开工较快 | 与 D-A1 已确认的第一期范围不一致，需显式修订 D-A1 |
| 修改后保留 | 只做命令执行和结果记录，不做独立验收 | 实现量较小 | 自评结果仍可能被误认为验收结论 |
| 延后 | 待条件明确再裁决 | 暂时不增加验证复杂度 | 任务关闭缺少可判定依据，证据链断裂 |
| 删除 | 不由 Skill 验证执行结果 | 范围最小 | D-E6.4、D-I1/I2 和证据闭环失去前提 |

**推荐答案**：保留，第一期。

**推荐理由**：执行结果只有经过 DoD 和验证步骤的实际比对，才能形成可审计的完成结论。独立验收还能避免执行者把自评当成通过结果。

**用户结论**：采纳“保留-第一期”，采用完整执行验证循环和独立验收：每个任务按 DoD 与验证步骤逐条重跑并比对实际结果，保存验收证据；由独立 Verifier 复核，执行者自检通过不得直接作为任务关闭依据。（2026-08-26 确认）

**状态**：✅ 已确认（`confirmed`）

**验收标准**：每个任务的验证步骤均实际执行并记录输出；结果按 DoD 逐条判定；第一期任务由独立 Verifier 重跑并给出验收结论；执行者自检通过不得直接关闭任务；任务关闭前保存命令输出、截图或 API 等对应证据。

**下游影响**：D-E6、D-E7、D-H2、D-H5、D-H7、D-I1、D-I2；D-L4 验证与独立验收相关能力分期。

### 决策点 D-A4：当前任务变更同步入口缺失

**问题**：Skill 是否提供一个以当前任务为范围的变更命令，由用户通过命令提出修改，Skill 在确认影响后同步修改当前任务相关产物并重新检查一致性？

**背景**：现状为所有产出单向"向前生成"，修改一个文档后前置/后续文档无同步机制，文档链随时间发散。需要一个用户显式调用的 `sync` 修改入口：用户提交当前任务的变更意图，Skill 先分析该任务内受影响的需求、设计、计划、验证步骤和代码，用户确认影响清单后再执行同步修改并复检。检查范围限定当前任务；发现共享文档可能影响其他任务时只提示，不自动修改其他任务。

**候选方案**：

| 处置 | 含义 | 代价 |
|---|---|---|
| 保留-第二期 | 第二期提供当前任务范围的 `sync` 修改命令：提案、影响分析、用户确认、同步修改、复检和归档 | 第二期实现量大 |
| 保留-第一期 | 提前到第一期 | 第一期范围扩大，与 D-A1 分期不一致 |
| 修改后保留 | 裁剪为仅冲突提示不做传播 | 下游不修复，基线仍会漂移 |
| 延后 | 待流程成熟再裁决 | 第一、二期变更靠人工同步，易漂移 |
| 删除 | 不做同步 | D-E8 与 D-J 域失效，长期不可维护 |

**推荐答案**：保留，第二期。

**推荐理由**：把变更收敛到显式命令和当前任务边界，既能避免直接改一处导致任务内文档分叉，也能避免一次变更误改其他任务；变更闭环不阻塞第一期状态/路由/执行验证闭环，因此放在第二期实现。

**用户结论**：采纳“保留-第二期”，采用当前任务范围的 `sync` 修改入口：用户通过命令提交修改意图，Skill 在用户确认影响清单后，修改源文档并同步修改当前任务相关产物，随后复检一致性并归档；其他任务不自动修改，仅提示潜在影响。（2026-08-26 确认）

**状态**：✅ 已确认（`confirmed`）

**验收标准**：用户可通过 `sync` 提交当前任务的修改意图；Skill 先生成该任务范围内的影响清单，未经用户确认不得写入；确认后修改源文档并同步当前任务相关产物，复检一致性并归档；对其他任务只输出潜在影响提示，不自动修改（对应 D-E8/D-J2）。

**下游影响**：D-E8、D-J 域；D-L4 提案生命周期分期。

### 决策点 D-A5：内容质量验收缺失

**问题**：候选问题 3 是否为真实要解决的问题？如何处置与分期？

**背景**：现状为评审只有结构性检查（章节/链接/格式），内容质量依赖人工审核，耗时大且不覆盖事实正确性。

**候选方案**：

| 处置 | 含义 | 代价 |
|---|---|---|
| 保留-第二期 | 事实分级抽查+多角色评审第二期实现 | 依赖第一期子 Agent 与证据机制 |

## 6. 单个决策点格式

每个原子决策点使用以下格式；不得只写问题和一个推荐字母。

```markdown
### 决策点 D-{域}{序号}：{主题}

**问题**：一个可被用户选择、否定或补充的问题。

**背景**：自含的问题背景：现状、候选素材中的既有方案（如有）、约束。不依赖外部文档即可理解。

**前置依赖**：必须先确认的决策点。

**已知事实**：用户输入、仓库事实或已验证配置。

**未知影响**：不确认会影响什么。

**候选方案**：

| 方案 | 内容 | 优点 | 代价 |
|---|---|---|---|

**推荐答案**：具体到可以直接实现或继续追问的方案。

**推荐理由**：依据、收益、代价和可能改变推荐的条件。

**用户结论**：记录原话、选择、补充约束和拒绝理由。

**状态**：⏳ 待确认（`unknown`） / `confirmed` / `not_applicable` / `blocked` / `conflict`。

**验收标准**：确认后可观察、可执行或可检查的结果。

**下游影响**：阶段、命令、产物、状态、测试和后续问题。

**逐项确认记录**（同一决策点含 2 个以上简单子项时提供；独立问题不得放在这里）：

- 子项为同构二元裁决（采纳/不采纳、支持/不支持）→ **汇总表格形态**：

| 子项 | 推荐结论 | 用户结论 | 状态 |
|---|---|---|---|
| D-{域}{序号}.{n} {子项} | … | 待确认 | `unknown` |

- 子项仅是同一决策点下同构的简单二元确认（例如采纳/不采纳、支持/不支持）→ **汇总表格形态**。如果子项需要独立的处置方式、分期、优先级、理由、验收指标、依赖关系或下游影响，则它本身就是原子决策点，必须升格为同级 `D-{域}{序号}`，不得使用 `D-{域}{序号}.{n}` 或五级标题承载。
```

**状态聚合规则**：使用汇总表格子项的决策点，其状态由子项聚合得出——

- 全部子项为 `confirmed` 或 `not_applicable` → 决策点 `confirmed`；
- 任一子项为 `conflict` → 决策点 `conflict`，暂停依赖它的下游问题；
- 任一子项为 `blocked` → 决策点 `blocked`；
- 其余情况 → `unknown`。

## 7. 动态问题和条件展开

每个决策点记录 `depends_on` 和 `unlocks`。

1. 只展示前置依赖已确认的问题；
2. 用户否定上游能力时，将依赖问题标为 `not_applicable`，并记录理由；
3. 用户新增约束时，重新计算受影响的问题、推荐和下游产物；
4. 用户修改已确认结论时，保留旧版本并创建新的变更决策记录；
5. 发现冲突时暂停下游，不用后来的回答覆盖早先结论；
6. 推荐答案发生变化时，记录推荐版本和变化原因。

## 8. 完整性自检

AskMe 完成前必须执行决策域完整性自检，替代对外部文档的覆盖担保：

| 检查域 | 完成条件 |
|---|---|
| 域覆盖 | §5 A~N 各域已展开；对照 §4 依赖链无遗漏域 |
| 子项闭环 | 所有逐项确认记录无 `unknown` 残留；每项有结论或显式处置 |
| 假设清零 | 无未消化的 `assumption`（已转为 confirmed/unknown/blocked 之一） |
| 冲突清零 | 无未裁决 `conflict` |
| 阻塞登记 | 全部 `blocked` 项有阻塞原因和恢复动作 |
| 条件展开 | 所有条件问题（M 节）触发条件已判定；适用者已确认，不适用者记录理由 |
| 延迟确认 | 延迟确认清单每项有归属阶段；无应属于 AskMe 的内容被延迟 |

发现遗漏时：新增决策点或子项，并回到对应依赖位置继续确认，不得带漏完成。

### 9.2 完成输出

AskMe 完成时必须落盘并输出：

1. 全部决策点、子项、方案、推荐、用户结论、理由、状态和时间；
2. Project/Feature 分支和七个命令契约表；
3. 状态、文档、配置、代码、测试、运行时和证据清单；
4. 风险档位、条件能力和未纳入范围；
5. 完整性自检结果；
6. 延迟确认清单（含归属阶段）；
7. 未决项、阻塞原因和恢复动作；
8. 可直接消费的总体设计输入包；
9. `next_steps: ["overall"]`。

总体设计只能消费 `confirmed` 和 `not_applicable` 内容。`recommendation`、`assumption`、`unknown`、`blocked` 和 `conflict` 不得静默进入总体设计。

## 10. 状态和跨会话恢复

每轮问答后保存：

| 字段 | 内容 |
|---|---|
| `design_subject` | 当前设计对象 |
| `decision_register` | 决策点、子项、方案、推荐、用户结论、状态和版本 |
| `known_facts` | 已确认输入和证据 |
| `unknowns` | 尚未确认的问题及依赖 |
| `assumptions` | 临时假设和验证责任 |
| `blocking_items` | 阻塞原因和恢复动作 |
| `last_question_id` | 中断后的恢复位置（可指向决策点或简单子项编号，如 `D-A11.3`） |
| `next_steps` | 下一个可问问题或后续命令 |

用户说"继续"时，从 `last_question_id` 之后第一个依赖满足的待确认问题恢复；不能重新开始，也不能用重复描述覆盖已有结论。

## 11. 交接规则

AskMe → 总体设计的交接必须包括：

- 已确认目标、用户、场景、对象和范围；
- 已确认流程、命令和分支契约；
- 已确认状态、文档、配置和产物边界；
- 已确认质量、证据、执行、评审和同步规则；
- 条件能力是否适用及其触发条件；
- 完整性自检结果和延迟确认清单（含仍需在详细设计阶段确认的实现项）。

总体设计不得消费 `unknown`、`assumption`、`blocked` 或 `conflict`，但可以接收已明确标记为详细设计阶段确认的延迟项。
