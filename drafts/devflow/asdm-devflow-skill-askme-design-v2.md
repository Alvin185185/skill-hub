# asdm-devflow AskMe 设计（v2 · 新形态）

> **本文件是什么**：`asdm-devflow` skill 的 AskMe（需求澄清）阶段设计，采用「大事 + 结论」的新形态，逐块生长。
>
> **为什么重写**：旧文件 `asdm-devflow-skill-askme-design.md` 把需求摊成 131 个原子决策点、每个 12 字段、还连依赖线——细节对过、但太碎太乱，无法用来捋思路。本文件把它归并成十几件「大事」，每件只保留 AI 生成下一阶段（overall/detailed）真正需要的料。
>
> **旧文件的去向**：`asdm-devflow-skill-askme-design.md` 原地保留，作为素材库，不删除；等本文件长全后再退休。
>
> **每件大事的写法（四段）**：
> 1. **要解决什么** —— 一两句话说清痛点。
> 2. **已确认结论** —— 写死、具体、可执行；这是喂给 AI 的料。压缩到「AI 读完不用猜就能写出下一层」为止，不替 overall 做设计。
> 3. **待定岔路** —— 还没拍板的选择，如实标「未定」，提醒 AI 此处不能往下生成、须回来问。终局态此段应清零。
> 4. **实现线索** —— 给后续阶段的提示，非本阶段要拍的内容（可选）。
>
> **写作约定**：
> - **只写正面终局事实**。凡是「删除／不再／取代／曾经／原 X 改为」这类只相对旧版本才有意义的表述，一律不进本文件；若某条「不要做 X」是给未来的硬约束（防止倒退），改写成正面禁令的口吻保留。
> - **只写需求澄清层的结论**，不写实现层细节（存储形态、字段 schema、具体命令实现等留给 overall／detailed）。
>
> **待验证**：这种形态终局喂 AI 能否产出合格 overall，最终以「第一次真拿某一节去生成 overall」的结果为准；若 AI 卡住，就把卡住处补实、校准颗粒度基准。

## 做什么（首要目标）

### 要解决什么

- 除明确标为**非目标/不适用**的能力外，纳入范围的每项能力都必须在本 skill 内**完整定义、完整实现、并具备验收证据**。

## 自持边界

### 要解决什么
skill 自己独立运行，还是依赖外部的流程系统、状态服务、任务数据库、上报服务。

### 已确认结论
- **完全自持**：状态、协议、索引、编排、运行时验证全部由 skill 自己提供。
- 外部工具只能作为**可探测、可替换的底层工具**，不能成为流程前置依赖；**不引入外部上报服务**。
- 没有任何外部流程系统时，仍能独立完成状态、文档、执行记录和复核。
- 适配层可在详细设计阶段讨论，但**不作为流程前置**。
- **联网获取外部资料（如开源仓库代码、同类项目）属于"取数据"，不构成流程前置依赖**：它和"依赖外部运行时服务/状态服务"是两回事——不联网时降级到本地资料仍能把流程跑完，只是借鉴质量下降并标 assurance 降级。故联网能力与"完全自持"不冲突。

### 待定岔路
无（本件已拍板）。若将来出现"必须复用的既有内部服务"，届时再作为例外单独澄清。

## 工作对象模型

### 要解决什么

## 主流程形状

### 要解决什么
Project 和 Feature 走怎样的主流程、有哪几个阶段、`sync` 和主流程是什么关系。

### 已确认结论
- **六阶段阶段闭环**，Project 和 Feature 共用同一骨架：
  `AskMe → Verify → Review → Overall → Verify → Review → Detailed → Verify → Review → Breakdown → Verify → Review → Execute → Verify → Review`
- 每个阶段是**"阶段执行 → 阶段产出 → Verifier 验证 → Reviewer 评审 → 门禁判定"**的闭环；**Verifier 未通过或 Review 未通过均不得进入下一阶段**，否则在当前阶段返工。
- 每阶段由 **Coordinator 编排一个或多个 Worker 产出**，由**一个或多个 Reviewer** 按阶段专属评审重点独立验收；支持流水线和人工两种运行方式。
- **Verifier** 按阶段的 DoD、契约和验证步骤实际核验，输出 `pass/fail + 证据`；只有 Verifier 通过且 Reviewer 通过，阶段才可进入下一阶段。
- **`sync` 是横切命令**：可在任意工作文档被指出错误或发生变化时调用，经影响分析和用户确认后修正上下游；无变更时不产生空阶段。
- 保留 **7 个用户命令**（askme/overall/detailed/breakdown/execute/review/sync）；UI、运行时、代码理解等作为**对应阶段的内部能力**，不单独成命令。
- 真人在规定门禁，以及命中需真人裁决的条件（不可逆/契约/安全/合规等）或冲突时，承担最终审核与裁决。

### 待定岔路
无（主流程形状已拍板）。**注**：各阶段命令的**具体契约**（detailed/breakdown/execute/Review 的输入/输出/门禁）见「命令契约」一节，那里仍有待定项。

## 角色模型

### 要解决什么
真人和 AI 各担什么职责、AI 干活时怎么配专业视角。

### 已确认结论
- **AI 四角色**：
  - **Coordinator**——拆执行单元、定依赖、分派、汇总；不实施、不验收、不覆盖失败结论。
  - **Worker**——负责一个执行单元、一个主要实施视角；不能验收自己的结果。
  - **Verifier**——负责一个明确验收范围，按 DoD/契约/验证步骤实际运行，输出 pass/fail + 证据。
  - **Reviewer**——负责一个主要评审视角，挑战需求/设计/实现本身；不修改被评审对象。
- **真人**只负责确认（需求范围、验收标准、最终结果）和裁决（预期不明、分歧不收敛、验收争议时）。
- **专业视角**（产品/前端/后端/测试/架构/UX/安全/契约…）是 Agent 的视角配置，**不是新的流程角色**。需要多个独立视角时，创建多个对应 Agent。
- 角色配置和真人裁决必须依据**统一、可判定的条件体系**，不能依靠模型临场判断。

### 待定岔路
无（本件已拍板）。

### 实现线索
Overall 阶段确定“事实 → 触发的能力/角色 → 是否需要真人裁决”的规则形状，Detailed 阶段确定具体实现。

## 状态权威

### 要解决什么
跨会话恢复所需的阶段和执行状态，存在哪里才不会产生多份、互相不一致。

### 已确认结论
- **实际工作文档即唯一状态权威**：阶段状态记录在对应工作文档，执行步骤状态记录在 Breakdown 产出的开发任务文档；这些受控状态块和步骤表是唯一权威来源。
- **`INDEX.md` 只负责定位**对象和工作文档，不承载详细阶段/执行状态。
- 结构化 JSON 只作为**当前命令的响应摘要**，不落盘充当状态。
- skill 只能通过结构化解析器读写状态块；用户手工改动后也必须先校验 schema。
- **依赖靠声明产生**：产出一个结论时，产出方必须写清"我这条基于谁"。未声明的依赖视同悬空，与「代码理解层」的"严格反假设"同一底线。
- **依赖有两种，都进依赖图**：文档内（决策点基于同篇另一决策点）、跨文档（下游文档基于上游文档结论）。每条依赖边带**版本戳**，记录"引用时被依赖项处于哪一版"。
- **依赖图是「一致性与变更」两套机制共用的地基**：报警器用它比对版本，Review 用它圈定"该读哪几篇的哪几处"。
- **报警器属于状态权威**：机械比对版本戳，被依赖项版本变化而引用方未跟上时报 stale。它只输出 stale 标记，全程不读内容、不判断对错、不重审上游质量。
- **报警器为事件触发**，只扫本次改动节点连着的边，双向（改文档→查其发出的边；改结论→查引用它的边）。兜底时机：变更关闭前全量扫、跨会话恢复时扫。
- **代码图谱独立维护，不并入依赖图**：设计或验证使用代码信息时，引用经过回源核实的代码调研产物；该产物记录来源文件/行号、代码 commit、图谱版本和核实结果。依赖图记录工作文档或工作产物对该代码调研产物的依赖。
- **代码变化不自动修改或同步文档**：报警器只做版本或引用失效提示，不判断文档与代码的语义一致性；一致性由 `Verify → Review` 发现、核实和判断，确认需要修改文档后才调用 `sync`。

### 待定岔路
无（本件已拍板）。

### 实现线索
状态块和步骤表的具体字段 schema、解析和读写方式归实现层细化。

## 代码理解层

### 要解决什么
AI 在现有代码库里工作时，上下文装不下、靠边读边猜，导致找错文件、臆造不存在的函数和调用关系。本层通过预解析把代码变成可查询的结构，降低这类错误。

### 已确认结论
- 本层产出一张**语言无关的代码图谱**：任何语言的代码都归一化成同一套抽象对象与关系。
- **降幻觉机理是硬要求**：调用、继承、依赖等代码事实必须来自**对代码的精确解析**（AST／类型系统／编译产物等语言各自的精确手段），**不允许由 LLM 推断代码事实**。
- **解析由 Coordinator 按语言派 worker 完成**：一个项目可多语言并存（如后端 Java + 前端 TS），各 worker 各自解析，**结果汇入同一张图谱**。
- **本层是 devflow 内部一个边界清晰的能力模块**：现阶段不独立拆出，与执行、评审、变更等能力平级；设计上保持清晰边界，以便将来可整体拆为独立 skill。
- **向设计流程提供的接口是"查询"**：设计／拆解／评审阶段通过查询图谱获取"这个方法被谁调用、改它影响谁、这个接口有哪些实现"，而非重新扫源码；状态需跨会话保持。
- **变更影响分析 = 反向调用链查询**："改 X 会波及谁"由图谱的"被调用"关系直接回答。
- **回源核实，图谱不是最终事实**：图谱只做导航和影响分析加速；凡要写进设计的代码事实，必须回到源码/类型系统核实，**无法回源的只能标"待核实"，不得直接当事实写入**。
- **严格反假设**：不允许臆测输入文档结构、现有模块、接口、技术栈；描述存量系统前必须有解析证据，具体字段/签名/版本/端口无来源就标"假设"或"需在执行时确认"，路径先验证存在。**未标注的假设等同编造。**
- **图谱失效要显式降级，不静默使用**：图谱不存在、代码变了（commit 变化）或解析有未处理错误时，依赖它的设计/同步结论必须标 `stale` 或 `assurance=degraded`，退化为逐次检索分析；greenfield 允许图谱未初始化，但要标基线状态并在基础任务中建立。
- **代码调研产物可冻结、可引用**：调研结论落成按仓库组织的产物，每条发现带文件/行号来源、可被设计文档按编号稳定引用，并记录图谱版本与回源核实结果。

### 待定岔路（未拍板）
1. **图谱的对象与关系类型清单**——具体定义哪些对象（代码单元／类型／可调用体／外部依赖…）和哪些关系（包含／依赖／调用／被调用／继承实现…）；够用即可还是求全。**未定前，overall 不得自行假设图谱 schema。**
2. **第一版落地哪些语言的 worker**——建议与手头项目主语言一致。
3. **是否纳入代码特征识别**（复杂度／API 端点／数据模型／测试方法识别等）及纳入哪些。
4. **跨语言调用如何在图谱中连接**（如前端调后端 API）——多 worker 结果的合并规则。

### 实现线索（给后续阶段，非本层要拍）
Java worker 可参考已有的 `asdm-ontology` 实现（javap 字节码解析等）；其余语言各选其精确解析手段。图谱的存储形态、查询接口形式、规模／增量／并发写等工程约束，留待 overall／实现阶段设计。

## 自主、稳定与人机协作（总纲）

### 要解决什么
这套 skill 的底座定位是：让 AI 尽量独立跑完"挖需求→找同类设计→设计→开发→验收"全流程，人是安全网而非驾驶员。但两件事必须先解决，否则"自主"就是空话：一是**出错了怎么自愈、错误知识往哪沉淀**；二是**换个弱模型，产出还稳不稳**。这一节定的就是驱动整套 skill 自我修正与跨模型稳定的底层机制。

### 已确认结论

**1. 单入口分诊。** 错误只有一种露头方式——**产出错了**（跑出来的设计/代码对这个项目不对）。不预设错误类型，一律从"产出错了"入口进，往回追根。

**2. 追根只落两类根因，判据是反事实测试。**

> 判据：假设该知道的都告诉它了，现有流程能不能自己接住这类错？
> - **能** → 经验问题：流程环节都在，只缺一条具体知识。
> - **不能** → skill 问题：流程里根本没有环节会消费这类知识（机制上拦不住）。

即：错在**知识**，还是错在**机制**。

**3. 两条修复线，不对称。**
- **经验问题 → 加经验，绝不改 skill。** 什么想不到都往 skill 里塞，skill 会越来越臃肿、越来越不通用。护住"精简通用"是硬约束，不是偏好。
- **skill 问题 → skill 只负责"识别 + 记录"成升级项**，到此为止。

**4. skill 不改自己是底线。** skill 升级项跨出 skill 边界后由人接手：人把 asdm-devflow 自己当成一个待开发项目，再驱动这个 skill 走正常流程去改它——是"人拿 skill 当项目、驱动 skill 迭代 skill"，skill 始终是被驱动的工具，永不自我修改。这也顺带证明了它的通用性：连自己都能当项目跑一遍。

**5. 经验体系：三层层叠。** 全局为底 → 项目类型 → 具体项目，读时合并，**越具体越赢**（项目盖类型、类型盖全局）。

**6. 存储切分 = 自动化边界 = 爆炸半径，三线重合。**

| 层 | 存哪 | 写入方式 |
|---|---|---|
| 具体项目 | schema/文件，随 repo 走 | 运行时自动维护、自动回灌 |
| 项目类型 | DB | 要证据（多项目复现）或人把关 |
| 全局 | DB | 要证据或人把关 |

项目层半径最小、可自动改；类型/全局半径大、写入必须收口。项目层→类型/全局层的"提升"本就要跨存储（文件→DB），这一跨正好就是那个高半径、该把关的动作——提升从来不该廉价自动。拿不准落哪层时**默认落项目（窄），多项目复现再提升**。

**7. "改已确认基线"要先分清：设计错了，还是需求本来如此。** 前者改设计并回灌经验；后者基线没错，只是澄清需求。两条路处理完全不同，不能混。

**8. 稳定不单列支柱，它是同一引擎的另一个输入源。** "稳定"是 skill 的设计属性——靠流程约束成立，不靠模型聪明成立（尺子原则）。skill 自己测不了跨模型稳定（换不了模型，那是人操作的活）；人做跨模型实测、发现"某步只有强模型能过"时，同样进单入口分诊：先问一句这是**加条经验能兜住**还是**机制上拦不住**，前者进经验库，后者才记 skill 升级项。

### 待定岔路
- **项目类型怎么判定**（风险点）：三层的收益全押在"能稳定认出项目属于哪个/哪些类型"上，一个项目还可能同时属多类型（前端+后端）。若靠模型现场拍脑袋，这层就成了新的不稳定源，正犯尺子原则。判定须有明确依据（按技术栈/架构标签匹配，而非自由描述）——具体规则待定。
- **skill 升级项的记录格式**、以及人接手迭代的触发方式，待定。
- **经验的 schema / DB 结构**（三层各自字段、检索匹配方式）待定。

### 实现线索
- 三层层叠、读时 cascade、越具体越赢——与 rules（全局+项目）、gitignore（全局+本地）同构，可借鉴其加载合并方式。
- 分诊引擎是运行时报错和人工跨模型实测的**共同下游**，做成单一入口即可复用。
- 经验库与代码图谱、工作文档状态相互独立（此前已确认），不要耦合。

## 需求挖掘（跨阶段）

### 要解决什么
北极星要求这套 skill 能把"用户没说出来的需求"挖出来，而不是只记录用户明说的。难点有二：一是这种深挖在旧设计里全押"模型自己想得到该问什么"，强模型挖得出、弱模型静默漏，直接违背"跨模型产出要稳定"；二是需求不是只在开头浮现——架构画出来、真实代码查出来、写到一半都可能暴露新需求。所以需求挖掘必须是一条**贯穿全流程**的能力（各阶段按自己粒度挖，越往后越细），且它的"挖得全不全"必须**靠流程约束成立，不靠模型聪明**。本节定这条能力的骨架；"askme"阶段是它最集中的一次应用。

### 已确认结论

**1. 覆盖面清单当硬门禁，不是软提示。** 不用固定问卷（项目千差万别，死问题必错），但也不把"该覆盖哪些方面"丢给模型现想。做法：给一张"必须覆盖的面"的清单，askme 对清单上每个面，**要么给出确认结论，要么显式标"不适用+理由"，不允许静默跳过**。弱模型因此被流程逼着正面面对每个面，不会"根本没想到要问"。这把"挖得全不全"从靠聪明改成靠流程。

**2. 区分两层：覆盖面（要问哪些方面）稳定，问题内容（具体怎么问）全动态。** 清单只管"有没有覆盖到"，不管"怎么问"。每个面里具体问什么、生成几个原子决策、怎么追问，仍由模型按这个项目现场生成——灵活性一点不丢。清单保底板（弱模型够得到），不封天花板（强模型可在清单外自由深挖新面、新问题）；稳定性来自"地板不依赖聪明"。

**3. 清单来源＝内置基线 ⊕ 经验库。** 内置基线是 skill 自带、固化、随 skill 版本走的默认清单（全局面 + 常见类型的初始清单），**不进经验库**；经验库是运行时长出来的增量，空着起步。读取时两者叠加、内置基线打底，**空库也能靠基线满血运行**，冷启动问题消失。某个面在经验库反复出现、证明普适时，由人在下一次 skill 迭代提升进内置基线。这又是一次爆炸半径分层：内置基线改动影响所有项目、要人把关、随版本；经验库自动长、半径小。

**4. 全局层覆盖面（12 面，内置基线的底）。** 几乎所有软件项目都逃不掉的面，遇到缺的以后再加：

1. 目标与价值（要解决什么、成了什么样）
2. 用户与角色（谁用、各角色差异）
3. 范围与非目标（做什么、明确不做什么）
4. 核心场景与行为（主流程、关键分支）
5. 数据（核心数据、来源、生命周期）
6. 鉴权与权限（谁能访问什么、越权怎么处理）
7. 外部依赖与集成（依赖谁、被谁依赖）
8. 运行与部署约束（跑在哪、什么限制）
9. 失败与边界（错了怎么办、极端情况）
10. 验收标准（怎么算做完、可判定）
11. 风险与未知（已知的坑、待解的未知）
12. 运行环境与平台（目标 OS、桌面/移动/Web、浏览器/设备矩阵、平台专属约束）

UI/响应式/可访问性、数据血缘/幂等、参数契约等不在全局层，属于项目类型层，由类型判定带出。

**5. 项目类型是双轴，不是一根轴；覆盖面取所有命中值的并集。**
- **技术形态轴**（Web 前端／后端服务／CLI／含部署…）：可从仓库事实观测出来（有无前端框架、有无 HTTP 路由、有无 Dockerfile 等），**模型比对可观测事实自动判定**（用代码理解层去查）；greenfield 无代码时用技术选型意图。groundability 高，可自动。
- **领域场景轴**（电商后台／短视频平台／行业系统…）：仓库里查不到，只能从"目标 + 核心场景"结论里读。这一轴才是设计差异的大头，判错会在最要命处静默漏问。它 groundability 低，机制必须不同于技术轴——见第 6 条。
- 一个项目在两轴上各命中若干值（既是"后端服务"又是"电商后台"），覆盖面取并集。过度包含很便宜（多命中一个领域，最多多几个面被标 N/A），judged 时宁可多命中。

**6. 领域轴：模型提议 + 人确认，且判定前置到 askme 开场。**
- **前置定位**：askme 一进来先收一段初始需求，**立刻判领域**——领域是 askme 的输入而非产物，因为"是什么项目"决定了"该问哪些面"。等场景问完再判就晚了，前面的问题已在"不知自己是什么"的状态下问出去了。
- **判得出**（命中明确领域标记，如电商={商品、订单、支付、库存、购物车}）→ 模型提议"我看这是电商后台，依据 X/Y/Z" → 人确认或纠正。
- **判不出／模糊／多个都像** → 不硬猜，**作为 askme 的第一个原子决策直接问用户**。它没跳出流程，就是 askme 的第一问。
- 领域定 → 组装覆盖清单（全局 12 面 + 领域面 + 技术轴面）→ 才展开逐面深挖。领域轴比技术轴多这一道人确认，是因为它 grounding 不住，残余不确定正好交给"人当安全网"——差别来自 groundability，不是随意规定。

**7. 没见过的领域要能兜底（通用底座的必答题）。** 领域标记比对落空时（偏门行业，基线和经验库都没有），不卡住：**降级到"只用全局 12 面 + 纯靠现场深挖"**，并把这次记为"新领域候选"进经验库。跑完这个项目，人可决定是否固化成新领域类型。没见过的照样能跑（靠全局面兜底），且跑一次就多学一个领域。

**8. 覆盖面之间承认极简依赖，不做成依赖网。** 绝大多数面平铺；只对少数"触发型"面标一条触发条件（如"数据涉及个人信息 → 触发合规面"，"运行环境=Web 多租户 → 加深鉴权面"）。刻意不重演旧设计 131 点那种密密麻麻的依赖网——多数依赖留给模型现场处理，只固化少量真正的触发关系。

**9. 完成门禁可判定，两道机制管两种漏。** askme 何时算完：**每个覆盖面都有结论或标了 N/A（硬门禁）+ 无悬空的 unknown/conflict + 阶段 Review 通过**。"清单过了"是必要条件（地板，管"没想到问"这种静默漏），Review 管深度（天花板，管"问得浅"）。两道一起才算完，不靠模型"觉得差不多了"。

**10. 经验回补闭环（接总纲）。** 后续阶段或人工发现"某个该问的面清单里没有""某个领域没见过"——这正是总纲那条"需求阶段没拦住"。分诊为经验问题 → 补进经验库对应层（面补进类型/全局面清单，新领域补进领域库）。清单于是越用越全，靠经验库自动长。

### 待定岔路
- **技术形态的条件库**：各技术形态值 + 各自的命中条件（可观测事实）+ 各自带出的覆盖面——要专门列一张表，初始由内置基线给一版，遇新形态经经验库长。
- **领域库**：各领域值 + 特征标记 + 各自带出的覆盖面——同样专门列表，初始内置一版，遇新领域经经验库长。
- **全局 12 面的最终增删**：现列 12 面是初版底，实际跑起来可能要加（如合规、可观测性、成本）或合并。
- **领域前置定位的判定粒度**：开场那段初始需求要多少信息才够判领域？判不出时问几轮才降级到"新领域候选"兜底？
- **项目类型判定的滚动精化**：greenfield 先靠意图粗判，随代码长出来再靠事实精化——精化到什么粒度停、何时重判，待定（与「代码理解层」的刷新时机相关）。
- **触发型面的清单**：哪些面是"触发型"、触发条件怎么写，需在条件库/领域库里一并定义。

### 实现线索
- 覆盖清单的"读取时叠加"（内置基线 ⊕ 经验库三层）与总纲经验库的 cascade 是同一套加载合并机制，可复用。
- 技术轴判定直接调「代码理解层」查仓库事实，不另造扫描器。
- 领域标记比对是"已确认场景结论 match 标记集合"，是集合运算不是自由判断——实现时把它做成显式的 match，而非交给模型自由发挥。
- 完成门禁的"每面有结论或 N/A"是可机器检查的状态，落在 askme 工作文档里（状态权威唯一），不另起状态文件。
- 本节是跨阶段能力，与「代码理解层」「同类借鉴」并列；overall/detailed/execute 各阶段都会再调它做本阶段粒度的需求挖掘，具体挂接点在「主流程形状」定义。

## 同类借鉴（跨阶段）

### 要解决什么
北极星要求这套 skill 能"找到同类项目、把好设计吸收进来"，而不是只凭模型脑子里的印象拍设计。难题是 **grounding**：模型很容易从训练记忆里"想起"一个其实不存在、或记岔了的同类项目/设计，把臆造的东西当好经验吸收——这跟代码幻觉是同一类病，却一直没有同一类药。所以借鉴必须**落在真实、可打开、可核实的来源上**，且"找得准不准"要**靠流程约束成立，不靠模型会不会搜**（否则强模型搜得准、弱模型搜得烂，又违背跨模型稳定）。它也是一条**贯穿全流程**的能力：需求阶段吸收"别人想到而用户没说的需求点"，设计阶段吸收"架构与设计取舍"，各阶段力度不同。

### 已确认结论

**1. 四类来源不是并列，是一条"提议→取真→沉淀"的链。** 适应性和增长来自沉淀，不来自模型临场聪明：
- **训练记忆 → 降级成"查询种子"，绝不直接吸收。** 模型"想起"的同类项目只是一组**候选名/搜索关键词**，不是可吸收的设计。它的产出只能喂给后面几类去核实；不落到一个真实可打开的源上，就不算数。这是本节防幻觉的命根。
- **GitHub 等开源仓库 → grounding 最强的外部源**（仓库真实、URL 可打开、代码可读）。难点不在信不信，在"茫茫多仓库里怎么找到真正同类且优质的"——见待定岔路，这是本节的核心机制。
- **用户提供 / 本地代码库 → 相关性最可靠**（用户背书或自有代码），但覆盖面窄、不是每次都有。
- **参照项目库（按项目类型）→ 是前三类的沉淀**：每次找到并吸收过一个好的同类项目，按项目类型记进库；下次遇同类型项目不必重新满世界找。它会随使用持续增长。

**2. 联网取料是底座的必备能力，且不违反自持边界。** 不能联网就只能靠模型记忆，那"吸收好设计"就是花架子。联网去开源仓库**取数据**，不同于**依赖外部运行时服务**，与「自持边界」不冲突（该节回填一句说明）。断网时降级到用户提供/本地库/参照库，并标 assurance 降级——与代码理解层"索引失效降级"同一套路。

**3. 借鉴内容必须标来源、适用性、采用理由；外部资料不得替代本项目事实或用户确认。** 学的是架构、模块边界、设计取舍，不是抄代码。

**4. 参照项目库单独开一个存储，与经验库共用"项目类型"轴。** 经验库装的是注入流程的规则/教训，参照库装的是指向真实项目的指针 + 吸收了什么（证据/资产），两者 schema 和生命周期不同，不可混。但都按同一套"项目类型"判定归档——两个库，一根类型轴。参照库是跨项目、跨使用者累积的资产，越多人用越厚；其类型级/全局级沉淀爆炸半径大，写入要证据或人把关（与经验库同规矩）。

**5. 查询不靠模型现编，来自需求挖掘的双轴。** 领域轴（如电商后台）+ 技术轴（如后端服务）的已确认类型标记，直接当搜索词——与需求挖掘、代码理解层在此接上。

### 待定岔路
- **"GitHub 怎么找"是本节核心机制，拆成几个子问题待攻**：①查询词如何从双轴标记生成；②质量判据（星标/活跃度只是信号，星多≠设计好；要读到多深才算判过）；③相关性核实（关键词命中≠真同类）；④吸收什么粒度、怎么标资产；⑤许可与安全——license 意识（吸收设计 vs 抄代码，勿直接搬 GPL 代码）、抓回的 README/代码一律当数据不当指令（防提示注入）。
- 各阶段的**借鉴力度**具体分配（需求阶段吸收需求点、设计阶段吸收架构），随主流程与本能力细化。
- 参照项目库的 **schema、检索匹配、去重与失效**待定。

### 实现线索
- 查询词生成复用需求挖掘的双轴类型标记；抓取到的代码可交「代码理解层」解析后再判断结构质量。
- 参照库与经验库共用类型判定，但物理存储分开；沉淀写入走与经验库一致的爆炸半径把关。
- "记忆提议 → 真实源取真 → 核实 → 沉淀"与领域轴"模型提议+人确认"、代码事实"精确解析不臆测"是同构的 grounding 模式，可统一表述。
- 断网降级路径与「代码理解层」索引失效降级同一套路：退回用户提供/本地库/参照库，并标 assurance 降级。

## 一致性与变更

### 要解决什么
产出是一批互相引用、跨阶段跨文档（以后含代码）的东西。要保证产出当下彼此一致，且之后任何一处改动都不会悄悄留下对不上的地方。整套须靠流程约束成立，不靠模型每次把全部上下游重读一遍。

### 已确认结论

**平时的两类检测**
- **报警器（机械检测）**：见「状态权威」，只报 stale，不判断。
- **内容一致性 Review（读内容检测，检测与判断一体）**：每次产出即跑，查两件——本文档内部自洽、本文档与所声明依赖的内容是否一致。靠依赖图圈定范围，只读所声明依赖的那几处，不全量重读上游。Review 能读出的不止"对不上"，还包括方案不成立、遗漏、逻辑打架等，发现问题的同时带出初步判断。

**发现不一致后的处理**
- **定位（内容层）**：判问题的根在本文档还是在被依赖项。被依赖项是已固化的已确认结论，推定其权威；冲突时默认根在本文档，仅当有明确证据推翻上游才判为上游问题。
- **改本文档**：根在本文档且本文档未固化时，直接改；本文档已固化时，改动须走变更工单。
- **改上游**：根在被依赖项（已固化）时，评审方无权直接改，发变更工单去改上游。
- **是否升级为出错分诊**：按性质，不按频率，沿用总纲的反事实测试——能靠补一条经验/约束避免的，是经验问题，加经验（全局/类型/项目对应层），不动 skill；机制根本无环节可拦的，是 skill 问题，记升级项，人驱动迭代，skill 不自改。

**变更全过程**
- 触发来源两个：用户直接提出；出错分诊判定为内容层可改（见总纲）。入口是 sync 命令。
- 步骤：根因定位（不打表面补丁）→ 影响分析（顺依赖图算波及面，含文档链与代码网络）→ 改动执行（同样起 Coordinator/多角色，投入由适用的条件触发决定，见「角色模型」）→ stale 传播 → 重新验收（走整套校验，该跑的验证/测试也跑）。
- **stale 传播**：改被依赖项 → 报警器反向扫 → 引用方全部 stale → 分流（纯地址/编号变化自动改；涉及"该结论是否仍成立"的升级为 Review 项交对应角色）→ 若某篇因此改了内容，它作为别人的上游再触发 → 直到扫不出新 stale，收敛。
- **关闭**：关闭前全量引用扫一遍，无 stale 才准关闭本次变更工单。关闭指本次变更收工归档，与"进入下一阶段"无关。
- **归位**：变更是打断主流程来做的，关闭后回到被打断的位置继续。
- **留痕**：一次变更是一条有始有终、可回看的记录（开→影响→改→验→关），供分诊追根、升级项记录、跨会话恢复、事后审查使用。

**职责边界**
- 报警器只比版本、机械便宜，从不判"谁的问题"、不评判内容、不重审上游质量。
- "谁的问题/怎么改"只存在于内容层，归 Review 与后续处理。
- skill 不改自己：所有改动走独立工单，skill 层缺陷只记升级项，人当项目驱动 skill 迭代。

### 待定岔路
- 文档↔代码一致是否纳入本套机制（与「状态权威」同一岔路）。
- 新文档是否同样全套走（主动 Review + 报警器）——倾向"每次产出即跑"已涵盖，未与你最终确认。

### 实现线索
- sync 为横切命令，是变更唯一入口。
- 变更工单带 change_id，记录开→影响→改→验→关全过程。
- 出错分诊（总纲）判定内容层可改时，以其结果作为本章触发来源之一，判在总纲、执行在本章。

## 命令契约（接口/契约层）

### 要解决什么
七个命令是整套 skill 的接口层。要写死的是**契约之间的关联性**——有哪几个命令、每个的职责与门禁、门禁怎么一环扣一环、输出为什么统一成一个形状、以及"能力只在命令内部路由、不新增命令"这条铁律。每个命令内部由哪个能力实现、产出什么细节，下沉到对应能力章；本层只定接口，不铺任何单条命令的产出细节。

### 已确认结论

**命令集合**
- 七个命令：`askme / overall / detailed / breakdown / execute / review / sync`。六个主阶段各是"阶段执行 + 阶段 Review"闭环，`sync` 是唯一横切命令。
- **命令是框，能力往里插**：代码索引、UI、任务安排、需求挖掘、同类借鉴等都在命令内部被路由调用，不新增用户命令。这是本层铁律。

**门禁链（契约关联性的核心）**
- 命令 N 的进入门禁 = 命令 N-1 的阶段 Review 通过。六个主阶段由此串成流水线：askme✓→overall✓→detailed✓→breakdown✓→execute✓→review。
- Review 未通过则返工、阻塞或转 `sync`；不存在未经 Review 进入下一阶段的路径。
- 流水线模式（Coordinator 自动推进）与人工模式（用户启动/干预/重试/裁决）共用同一套门禁，人工不得绕过 Review。

**七命令索引（一句话职责 + 门禁，一碗水端平，不铺产出细节）**

| 命令 | 一句话职责 | 进入门禁 | 深度归属 |
|---|---|---|---|
| `askme` | 对身份已定的单一对象做需求访谈，产出可判定结论 | 对象身份已确定 | 需求挖掘 |
| `overall` | 概要设计 | askme 完成且决策点全确认 | 「阶段产出」 |
| `detailed` | 详细设计 | overall Review 通过 | 代码理解层 / 「阶段产出」 |
| `breakdown` | 实施拆解 | detailed Review 通过 | 「阶段产出」 / 证据与评审 |
| `execute` | 执行 + 验收 | 显式调用且开发任务文档有未完成步骤 | 角色模型 / 证据与评审 |
| `review` | 阶段 / 收尾评审 | 对应阶段产出已就绪 | 证据与评审 |
| `sync` | 唯一横切修改命令，可从任意工作文档调用；接口=（对象/源文档/位置/现状/目标改动/原因），门禁=用户确认后才写入 | 用户确认 | 一致性与变更（影响传播唯一认依赖图） |

**统一输出**
- 每个命令输出结构化 JSON 摘要（subject_type / subject_id / project_id / 命令 / 产出路径 / 结果 / 建议动作）；JSON 不落盘充当状态，状态权威在工作文档（见「状态权威」）。
- 门禁不满足即终止，输出缺失清单 + 补救指引。
- 命令文件按需加载：调度器路由后只读当前命令文件及其引用的规范。

### 待定岔路
- **各主阶段命令的"阶段内部深度契约"整条待确认**：detailed / breakdown / execute / 阶段 Review 的命令内部编排脚手架与产出细节仍待定，已随各自深度内容下沉到对应能力章，在那里标待定，本层不重复。

### 实现线索
- 各主阶段命令的**产出清单细节**（overall 的模块地图/端到端流程/页面清单/溯源硬规则、detailed/breakdown/execute 的产出）待"「阶段产出」 / 证据与评审"写成后下沉归位，本层只留索引。
- E1 的"阶段编排统一要求"与阶段 Review 统一规则是所有主阶段共用模板：谁来编排、谁来评审归「角色模型」，按什么顺序接线归「主流程形状」，本层只定"每命令有门禁、门禁=上一阶段 Review 通过"。
- sync 的影响传播唯一认依赖图（见「一致性与变更」）。

## 证据与评审

### 要解决什么
AI 自主推进时会"声称"自己做到了（设计对了、测过了、通过了），但可能是幻觉或偷懒。若系统直接采信这些声称，流程就成了自说自话，弱模型尤其如此，产出无法稳定。本章解决两件事：**用可核对的证据切断"自说自话"；用每次调整后的多角色评审作为推进闸门**，让 AI 靠"审过没有"自主判断能否进下一阶段，人只在命中需真人裁决的条件时兜底。

### 已确认结论

**证据：切断自说自话的实锤**
- 每一处"我做到了"的声称，都要有可被独立核对的证据支撑；拿不出或核对不上，即不算数。这与「代码理解层」的回源核实、独立 Verifier 实跑、严格反假设同一底线。
- 证据分三类，均须可追溯、可验证：代码事实（文件/行/符号）、运行时证据（命令、返回码、日志、截图、API 响应）、引用证据（决策点、设计位置）。
- **证据本体存独立的 evidence 文件区，不塞进文档；文档只留一行可回源指针**（路径/命令/commit/行号），指针挂在被证明的那条结论或步骤旁。
- 证据归属跟随被证明的对象：设计结论的证据落设计文档指向、执行步骤的证据落开发任务文档指向、访谈结论的证据落 askme 文档指向。
- evidence 文件区按"对象→阶段→任务/结论"分层，路径由 ID 机械推导（固定约定，不靠模型自由命名），使证据随对象、任务增多仍各归各位。
- 证据是状态的**佐证**，不是状态本身；状态权威仍只在工作文档（见「状态权威」）。证据进依赖图，代码/依赖一变，依赖它的验证结论自动 stale 并重跑（复用报警器，非新机制）。

**评审：唯一的推进闸门**
- **没有"阶段末"这一独立时点。** 一个阶段就一份文档，文档反复调整；每次调整后都跑同一种多角色评审，审通过即毕业进下一阶段，不通过则带意见返工。审通过就是 AI 自主推进的信号，不需人喊"可以进下一阶段"。
- **评审角色按需配置，不是固定班子。** 上哪些角色由可判定的触发条件决定（项目类型双轴 + UI/安全/数据/运行时等条件触发），不靠模型即兴，以保证弱模型不漏配。小需求天然角色少，故"每次调整都审"不会过重。
- 评审的**一致性维度**采信持续在跑的一致性检测结果（见「一致性与变更」），本章不重复定义；评审只额外做一致性之外的质量判断（内容质量、事实 grounding、风险覆盖、可执行性等）。
- 通过闸门：所有 blocking 问题清零才通过；冲突、规定门禁、命中需真人裁决的条件（不可逆/契约/安全/合规等）时必须真人最终裁决（与总纲"人是安全网"一致）。
- **审出问题一律走已定处理链**，无"登记偏差、欠债放过"的旁路：当场能改的改，根在已固化上游的发变更工单（见「一致性与变更」），缺信息无法判定的作未知项显式挂起（见「需求挖掘」），疑为经验/skill 缺口的转出错分诊（见「出错分诊」）。

### 待定岔路
- 本章无独有待定项。"评审上哪些角色、查多严"依赖的那套可判定触发条件（UI/安全/数据/运行时等强制真人裁决与角色配置的完整清单），与「角色模型」的"哪些条件强制真人裁决"是同一套条件体系，待统一梳理条件体系时一并定。

### 实现线索
- 证据文件区的具体目录 schema 与字段属实现细节，归后续「配置与文档」梳理，本章只定"分层归档、路径可推导、不自由命名"原则。
- 评审要查哪些点、查多严，由适用的条件触发决定（涉 UI/安全/数据/运行时各自触发对应角色与查验），无独立风险档位总闸。
- 审出问题疑为经验/skill 缺口时转「出错分诊」的分诊单元判类，本章不实现分诊逻辑。
- 评审"谁来编排、谁来评审"归「角色模型」，"每次调整后审、通过即毕业"的推进形状归「主流程形状」，本章只定"评审是推进闸门 + 证据是其依据"。

## 出错分诊

### 要解决什么
AI 自主跑流程，产出可能错。得有一个固定部件：把"产出错了"变成"哪类根因、怎么处置"，让 AI 自己把错收掉，收不掉的落到人。

### 已确认结论
- **单入口。** 错只有一种露头方式——产出错了（跑出来的设计/代码对这个项目不对）。不预设错误类型，一律从这个入口进，往回追根。
- **追根落两类根因，判据是反事实测试。** 能靠补经验/约束避免的，是经验问题，交经验章处置，不动 skill；机制上根本无环节可拦的，是 skill 问题，记升级项，skill 不自改，人拿 skill 当项目迭代。
- **判"经验问题"的前提是拿得出可回源、经过验证的经验根**；拿不出的，不算经验问题，自然落到 skill/人那条。经验根怎么验证、怎么入库归经验章。
- **分诊是一个被反复调用的单元。** 发现问题→分诊→分类→没经验就补经验→再试→又有问题→再分诊，同一判据每圈不变，靠环自身收敛，不设"复发""升级"等特殊态。
- **稳定同源。** 人做跨模型实测，发现"某步只有强模型能过"时走同一入口同一判据——补经验能兜是经验问题，机制拦不住是 skill 问题。

### 待定岔路
- 分诊判 skill 问题后，升级项记在哪、什么格式（见「经验的生命周期与可信度」/ skill 迭代记录）。

### 实现线索
- 分诊是各章的共同下游：一致性与变更、证据与评审发现问题都调这个单元，不各自实现。
- 反事实测试是唯一分类判据，「一致性与变更」章"是否升级出错分诊"沿用它。
- 经验的存储分层、补充、验证入库与纠错全归「经验的生命周期与可信度」章，本章只在"经验问题"处接过去。

## 经验的生命周期与可信度

### 要解决什么
经验库是这套 skill 跨项目变聪明的地方——它得能自己长（不然冷启动永远空）。但"自己长"有个反面：长歪了怎么办。经验一旦写进去就当真理用，一条错经验会污染后面所有项目。所以经验不能只有"入库"，得有一条完整的活法：怎么进、进哪层、用着发现不对怎么改、怎么被推翻。本章定这条生命周期，让经验既能自动长、又不会长歪固化。

### 已确认结论
- **三层存储、按层定入库严格度。** 全局 < 类型 < 项目，读时叠加、越具体越赢（见「状态权威」/总纲）。入库严格度按爆炸半径分：项目层半径最小 → AI 自动入库，不卡人；类型层/全局层半径大 → 必须有证据（多项目复发）或人确认才入。默认落最窄的项目层，反复被证明普适才升层。
- **项目层敢自动入库，前提是纠错出口敞开。** 经验不是石头，是活的：入库后使用中持续可优化、可整条推翻；哪层错就改哪层，类型/全局层的改动同样走"证据或人把关"。松的入口 + 敞开的纠错出口，合起来才安全——只要宽松不要纠错是不成立的。
- **经验入库必须绑定"作用坐标"。** 坐标 = 这条经验管哪个格子（需求阶段的覆盖面 / 设计执行阶段的环节·产出类型 / 三条跨阶段能力的环节）。坐标不是另立编码，就是流程本来就有的格子。它是复发识别和责任定位的地址，没有它经验就是笔无法追踪的糊涂账。
- **复发 = 同一作用坐标上，一条"本该管这里"的经验没兜住。** 靠"出错位置反查挂在那儿的经验"识别，不靠比对两个错误长得像不像（相似度靠模型主观判，是不稳定源）。复发只负责"发现问题 + 把嫌疑缩到这个坐标的经验集"，不自己定罪——具体是某条判错了、还是都对只是缺一条新的，交回分诊判（见「出错分诊」）。
- **坐标始终由分诊追根产出，与谁触发无关。** 不管问题是流程自审出来的、还是人/外部（人工测试、验收、上线后）发现的，都从同一分诊入口进，追根落到某个格子即为坐标。
- **人/外部发现"该拦没拦"会追出第二个坐标。** 比如"设计错了、流程却没测出来"：一个坐标落在出错的设计环节，另一个落在"本该拦住的验收/评审关"。第二个坐标交反事实测试判——那道关缺条经验就补经验，机制根本拦不住就记 skill 升级项。人发现的问题反而比自审多逼一层"关口为什么没拦住"。

### 待定岔路
- 一条经验好坏由谁 judge、拿什么验（候选→确认的验证机制细节）。
- 经验的 schema / DB 结构：三层各自字段（含作用坐标怎么编码）、检索匹配方式。
- 内置基线里某条反复出现的经验，升级进基线的判定与节奏（牵 skill 迭代）。

### 实现线索
- 本章是总纲经验体系（三层/爆炸半径/尺子原则）的落地细则，不重述哲学。
- "补经验/改经验/推翻经验"全由「出错分诊」判"经验问题"后接过来触发，本章定生命周期，分诊定何时进入。
- 覆盖面回补（需求挖掘）、领域库/参照库沉淀（同类借鉴）都是本生命周期的具体入库场景，共用"按层把关"规矩。
- 读取合并（内置基线 ⊕ 三层 cascade）与 rules/gitignore 同构，可复用其加载机制。

## 阶段产出

### 要解决什么
六个阶段每个都要交出可校验的产出，不能"感觉做完了"就过。这章把各阶段到底交什么、以及交付物必须守的硬规则定下来，让"这个阶段算不算交付了"有客观标准，弱模型也照单交付。已被专门能力章认领的产出（访谈结论、代码事实、UI 效果图、验收证据、状态/追溯）不在这里重写，只指过去；本章只收没被任何能力章认领的那部分阶段交付物。

### 已确认结论
**各阶段交付物（只列无主的部分，其余指回对应章）**
- askme：访谈结论——见「需求挖掘」（覆盖面结论 or N/A 硬门禁、领域判定、未知项挂起），本章不重写。
- overall（概要）：目标用户、产品模块地图、端到端业务流程、客户端/服务端/数据/基础设施边界、非目标、依赖、主要风险；Feature 分支另交总体概述、使用场景、受影响模块、与父 Project 的关系。受影响页面清单见「UI 能力」。空仓库记录 greenfield 基线与待选技术资产。
- detailed（详细）：后端 API 章节、可判定 DoD（初始全未完成）、假设集中清单。UI 设计章节/前端实现章节见「UI 能力」；基于精确代码事实见「代码理解层」；追溯并入依赖图见「一致性与变更」。
- breakdown（拆解）：纵向业务切片的任务集（每个任务=编号+类型化描述+依赖+交付物+验证步骤），任务内部可含多个执行单元。开发任务文档的步骤表（step_id/状态）见「状态权威」。
- execute（执行）：每步的执行记录（时间、角色、范围、命令输出摘要、重试、偏差）追加进开发任务文档。各类验收证据见「证据与评审」，编排见「角色模型」。

**阶段级硬规则（跨阶段通用的产出约束）**
- 溯源防镀金：场景、MVP Feature、每条设计结论必须可溯源到上游决策点/结论，溯源不到即视为镀金，不予通过。
- 不越阶段：概要不写字段级接口/组件树/任务细节；各阶段只产出本阶段该产出的粒度。
- DoD 可判定：详细设计的 DoD 禁止模糊表述，无法量化的必须给出人工验证步骤。
- 纵向切片强制：拆解按可独立验收的纵向业务能力切，禁止按技术层横向拆分；拆解前先扫描详细设计全部标题再语义定位（反假设，不臆测章节结构）。

### 待定岔路
- 各阶段交付物的模板骨架（固定锚点+受控扩展区）属实现细节，归实现层。

### 实现线索
- 本章只定"交什么 + 硬规则"；"谁来产出/评审"归「角色模型」，"按什么顺序、门禁"归「主流程形状」「命令契约」。
- 命令契约索引表里 overall/detailed/breakdown/execute 的"深度归属=「阶段产出」"即指向本章。
- 溯源、DoD 可判定、纵向切片等硬规则由对应阶段 Review 作为评审项检查（见「证据与评审」）。

## UI 能力（阶段内部能力）

### 要解决什么
涉及界面的项目，光有文字设计和后端接口不够——页面长什么样、交互怎么走、响应式和可访问性达不达标，这些是必须交付且必须验收的东西。UI 能力解决的是：让这套 skill 在需要时把界面部分也纳入同一条设计→实现→验收链，而不是留给模型口头描述、无从校验。它和代码理解、需求挖掘、同类借鉴一样，是 skill 内部一块条件触发的能力，不单独成命令、不拆独立 skill。

### 已确认结论
- **UI 是条件触发的内部能力**：只有项目涉及界面（页面、交互、响应式、视觉）时才触发；触发判定由项目类型层带出（需求挖掘双轴里的技术形态轴识别到"Web 前端/含界面"即触发）。不涉界面的项目完全不走这条链。
- **效果图（SVG）是视觉基线**：UI 设计阶段产出"截图级"的 SVG 效果图作为视觉事实来源，可 diff、开发前人和 AI 都能审、页面照它实现。它之于前端设计，等同代码事实之于后端设计。
- **UI 全链条走通用流程，不另起炉灶**：效果图产出 → 设计 Review 审图 → Worker 照图实现 → Verifier/Reviewer 对真实页面验证（截图比对、交互、响应式、可访问性、与效果图对照）。这些环节是「证据与评审」「角色模型」在 UI 上的具化，本章只点明"UI 会触发它们"，不重写其规则。
- **失败不降级**：效果图生成不出或不合格时，诊断 + 重试，最终标 blocked；绝不要求用户提供参考图、绝不自动降低视觉标准。与代码理解层、同类借鉴的"降级必须显式标记、不静默降级"同一底线。
- **效果图变更走依赖图传播**：效果图作为被依赖节点进依赖图，它一变，报警器反向扫、把引用它的实现/验收标 stale 重跑。不为 UI 单设固定传播链（与 sync 不设固定链同理）。

### 待定岔路
- 靠什么画 SVG（画图机制、自检项）属实现层，归实现阶段。
- UI 设计章节的产出清单（效果图引用、字段对照、组件清单、状态机）与前端实现章节，随「阶段产出」一起下沉细化。

### 实现线索
- UI 触发后，设计/实现/验收各环节复用「证据与评审」「角色模型」既有定义，不新增角色、不新增命令。
- 效果图作为视觉证据进依赖图，复用报警器的 stale 传播（见「状态权威」「一致性与变更」）。
- 触发条件的可判定化（哪些信号算"涉及 UI"）与需求挖掘双轴的技术形态轴同源，统一在条件体系里定义。
