## 1. 这一步要解决什么问题

用户通常不会一开始就提供一份完整的产品需求。他们可能只说：

> “给后台加一个批量导出功能，最好还能在手机上看。”

这句话足以表达方向，却不足以直接指导设计和开发。实现者还不知道：

- 导出哪些数据，谁可以导出；
- 一次导出多少条，采用同步还是异步；
- 导出失败如何提示，是否允许重试；
- 手机端是完整操作还是只查看结果；
- “最好”是硬性要求还是可选建议；
- 怎样判断功能已经完成。

AskMe 的职责就是把这种模糊意图，逐步整理成一组用户明确确认过的决策。它不负责决定技术实现，而是保证后续设计有清晰、可追溯、可验收的输入。

AskMe 完成后，用户应该能回答：

1. 这项特性为谁解决什么问题；
2. 做什么、不做什么；
3. 正常、异常和边界情况下应该怎样表现；
4. 哪些约束必须满足；
5. 用什么可观察结果判断它完成。

这些内容对应需求基线中的 AskMe 流程，详见
`asdm-devflow-skill-design.md` §1、§4.1。

## 2. 用户实际会经历什么

一次新特性的 AskMe 体验如下：

```text
用户描述想法
    ↓
Skill 识别新特性或已有特性
    ↓
读取项目配置、索引和当前状态
    ↓
对现有代码做必要的轻量确认
    ↓
展示第一个决策点、背景、选项和推荐
    ↓
用户选择并说明理由
    ↓
Skill 立即保存本轮结论和验收标准
    ↓
继续下一个尚未确认的决策点
    ↓
所有关键决策完成
    ↓
生成 AskMe 文档，允许进入 Overall
```

用户中途关闭会话后，再说“继续 FT-xxx”，Skill 不应重新开始，也不应依赖上一次会话的记忆，而是从持久化状态中找到第一个未完成决策点。

## 3. AskMe 的能力清单

AskMe 不是一个简单的问答模板，而是由以下能力组成的交互流程：

| 能力 | 用户看到的结果 | 主要产物 |
| ------ | ---------------- | ---------- |
| 特性识别 | 新建特性，或继续已有特性 | `feature_id` |
| 项目上下文读取 | 问题不会重复询问代码已经能回答的事实 | L0 调研引用 |
| 风险判断 | 知道需要轻量、标准还是完整流程 | `workflow_profile` |
| 决策点生成 | 每次只讨论可做选择的问题 | AskMe 决策点 |
| 选项和推荐 | 用户能理解不同选择的影响 | 选项表和推荐理由 |
| 用户确认 | 明确记录选择和理由，而不是猜测 | 已确认决策 |
| 验收绑定 | 每个决策都能转成可检查的结果 | 验收标准 |
| 增量落盘 | 中断后能够继续 | Markdown、`state.json`、INDEX |
| 完成门禁 | 未澄清完的问题不能进入 Overall | 阶段状态 |

## 4. 输入、路由和前置检查

### 4.1 可以从哪些入口进入

| 用户输入 | Skill 的解释 |
| ---------- | -------------- |
| 新的自然语言需求 | 创建一项新的特性并开始访谈 |
| `FT-xxx` | 打开指定特性，根据状态继续 |
| “继续”“下一步” | 找到最近一个未完成的特性或决策点 |
| “这里不对”“修正” | 这是变更或根因修正，转交 `sync` |

Skill 不能仅凭用户的一句话判断当前阶段。它必须先读取 `state.json`；只有旧特性完全没有状态文件时，才根据文档是否存在做兼容恢复。这一恢复规则来自
`asdm-devflow-skill-design.md` §6。

### 4.2 必须先读取什么

处理请求时按以下顺序读取：

1. 项目根目录的 `.devflow/config.md`；没有时使用默认配置。
2. `{docs_root}/INDEX.md`，用于定位特性和分配编号。
3. 目标特性的 `state.json`，若存在。
4. 目标特性的 AskMe 文档，若存在。
5. 当前请求涉及的最小代码范围，用于 L0 确认。

如果发现已有 AskMe 正在访谈，必须恢复它；不能因为用户重新描述了一遍就生成第二份同名文档。

### 4.3 初始化新特性

新特性初始化时需要：

- 根据 `feature_id_mode` 分配 `FT-xxx`；
- 确定特性名称和负责人；
- 判断是否涉及 UI、权限、数据迁移、外部契约等高风险信号；
- 选择 `light`、`standard` 或 `full` 档位；
- 创建特性目录、初始 `state.json`、AskMe 文档和 INDEX 条目。

编号分配不能只看当前会话中的数字，必须检查 INDEX 和已有目录，避免并发或中断后重复编号。

## 5. 风险档位如何影响 AskMe

AskMe 不需要一次性收集所有可能的细节，但必须先判断工作深度：

| 档位 | 适用情况 | AskMe 的做法 |
| ------ | ---------- | -------------- |
| `light` | 文案、局部配置、小缺陷 | 合并相近问题，但仍确认验收和边界 |
| `standard` | 普通业务特性 | 完整询问目标、范围、异常、依赖和非功能要求 |
| `full` | 权限、迁移、支付、公开契约、合规、不可逆操作 | 逐项确认风险、回滚、兼容、审计和验收 |

无法判断时使用 `standard`。执行中发现高风险信号只能升级，不能为了少问问题而静默降级。完整规则见基线 §3.4。

## 6. L0 现状确认

AskMe 会做少量代码调查，但它的目标是避免无意义提问，不是替代 Detailed 的深度调研。

### 6.1 什么时候调查

在提出一个决策点前，如果问题涉及现有路由、命令、接口、配置或已有功能，先搜索相关代码。例如用户说“增加导出”，Skill 应先确认项目是否已经有导出入口、权限检查或下载接口。

### 6.2 调查输出

每条能影响提问的事实都应包含：

- 文件路径；
- 行号或符号；
- 事实是什么；
- 这条事实如何改变当前问题。

例如：

```text
现有用户列表页已经有 /users/export 路由，
入口位于 web/src/routes/users.tsx:42，
但后端只支持单条导出，未发现批量接口。
因此本轮只需要确认批量上限和异步行为，
不再询问“是否需要一个导出入口”。
```

找不到证据时必须写“待确认”，不能把搜索不到当成“系统不存在该能力”。深度调用关系、跨仓库扫描和数据模型冻结留给 Detailed。

## 7. 决策点如何设计

一个决策点只解决一个会影响范围、行为、约束或验收的问题。每个决策点都由六部分组成：

```text
问题 → 背景与现状 → 可选方案 → 推荐 → 用户结论 → 验收标准
```

### 7.1 问题

问题要能让用户做出明确选择，例如：

```text
批量导出超过 10,000 条记录时，应该采用哪种方式？
```

不能使用无法判定的问题，例如“导出体验要好不好”。

问题不能来自封闭的固定问卷。运行时先读取用户输入、仓库事实、现有文档、风险和已确认结论，只为会影响目标、范围、行为、约束、风险或验收的未知项创建原子决策。目标、用户、MVP、数据、权限、UI 等只是覆盖检查维度；如果用户回答或评审发现新的未知项，必须追加新的同级决策。

### 7.2 背景与现状

背景由用户目标、L0 事实、已确认约束和该选择的影响组成。背景要帮助用户理解为什么现在需要回答这个问题。

### 7.3 选项

通常至少提供两个互斥选项，并说明优点、代价和适用条件：

| 选项 | 说明 | 优点 | 代价 | 适用条件 |
| ------ | ------ | ------ | ------ | ---------- |
| 同步下载 | 请求完成后直接返回文件 | 交互简单 | 大数据量容易超时 | 数据量小且稳定 |
| 异步任务 | 后台生成，完成后通知或供下载 | 可处理大数据量 | 需要任务状态和重试 | 数据量不可预测 |

只有一个合理选项时，也要解释为什么其他方案不成立。

### 7.4 推荐

推荐不是替用户做决定，而是给出基于证据的默认方向。推荐必须说明依据：现有代码、用户约束、风险档位或已确认的业务目标。没有证据的判断要标记为假设。

### 7.5 用户结论

只有用户明确选择、接受推荐或明确授权后，决策点才能变为已确认。沉默、转移话题和“都可以”不能自动变成确认；此时应追问偏好或记录待裁决。

### 7.6 验收标准

每个已确认决策至少绑定一条可观察标准：

- “P95 小于 500ms”，而不是“性能良好”；
- “无权限用户返回 403，并且页面不显示导出按钮”，而不是“做好权限控制”；
- “手机宽度 390px 时表格不出现横向溢出”，而不是“适配移动端”。

## 8. 对话循环

每轮 AskMe 都遵循同一循环：

1. 读取当前状态和上一次未完成的位置。
2. 从事实、风险和覆盖检查中选择下一个最重要且前置条件已满足的未知项；不得按固定问题清单顺序提问。
3. 做必要的 L0 确认。
4. 展示问题、背景、选项和推荐。
5. 等待用户回答。
6. 复述对用户回答的理解；如果回答含糊，拆成新的决策点。
7. 记录用户选择、原话理由、验收标准和证据。
8. 原子写入状态，再更新文档和 INDEX。
9. 如果仍有未决问题，展示下一轮；否则运行完成门禁。

一次回复不应把十几个问题全部倾倒给用户。`light` 可以合并相近问题，`standard` 和 `full` 默认按主题分批，每批最多三个相互关联的决策点。

### 8.1 决策依赖

问题之间有依赖时，先问上游选择。例如先确认“是否支持手机端”，再询问“手机端采用全页还是抽屉”；如果用户否定前一个问题，后一个问题不应出现。

### 8.2 模糊回答

用户回答“都可以”“按你建议”“先这样”时，Skill 应：

1. 说明自己理解的具体选项；
2. 说明该选择带来的影响；
3. 请求明确确认；
4. 把用户的新约束写入决策背景。

### 8.3 用户改变已确认决策

如果用户表示“刚才的决定改一下”，不能直接覆盖旧值。应停止当前流程，创建一次 `sync` 变更提案，保留旧值、新值、原因和影响范围。

## 9. AskMe 文档和状态文件

### 9.1 文档结构

AskMe 文档供人阅读，建议采用以下结构：

```markdown
# FT-xxx {特性名称} - AskMe

## 背景与目标
## 当前状态与现有能力
## 决策点
### D1 {问题}
### D2 {问题}
## 范围边界
## 假设与未决问题
## 验收标准汇总
## 访谈记录
## 修订记录
```

每个决策点包含问题、背景、选项、推荐、用户结论、验收标准和证据引用。文档中的状态是给人看的投影，机器状态以 `state.json` 为准。

### 9.2 状态转换

```text
不存在 → clarifying → completed
                 ├→ blocked
                 ├→ conflict
                 └→ stale
```

| 状态 | 含义 | 能否进入 Overall |
| ------ | ------ | ------------------ |
| `clarifying` | 仍有问题等待用户确认 | 否 |
| `completed` | 必要决策和验收标准齐全 | 是 |
| `blocked` | 缺少外部条件或用户裁决 | 否 |
| `conflict` | 当前文档与其他事实冲突 | 否 |
| `stale` | 上游事实已变化，需要同步 | 否 |

### 9.3 写入顺序

每轮确认都必须按以下顺序写入：

```text
校验新状态 → 原子写入 state.json → 更新 INDEX → 更新 AskMe Markdown
```

任一步失败时，Skill 要停止推进，保留恢复信息，并返回 `state_sync_error`。
不能出现 Markdown 显示已完成、但 `state.json` 仍是未完成的情况。

## 10. UI 需求的特殊处理

涉及页面时，AskMe 不负责画最终界面，但必须确认会影响后续设计的产品决策：

- 是否确实需要 UI；
- 入口是全页、弹窗、抽屉还是嵌入区域；
- 用户完成任务的关键路径；
- 复用哪套设计系统或组件库；
- 是否支持移动端；
- 可访问性目标是 WCAG A 还是 AA；
- 空态、加载态和错误态是否属于范围。

这些选择会被 Overall 的页面清单和 Detailed 的 UI 设计消费。AskMe 不应在这里决定具体组件名、CSS 属性或 API 字段。

## 11. 完成门禁

只有满足以下条件，AskMe 才能返回完成：

1. 所有当前已发现且会影响设计的决策点均已由用户明确确认；
2. 每个决策点都有可判定验收标准；
3. 范围内、范围外、假设、依赖和未决问题已经分开记录；
4. UI 特性已经完成 UI 相关决策，或明确记录“不涉及 UI”；
5. 关键现状事实都有可回源引用，未经确认的内容标为假设；
6. `state.json`、INDEX 和 AskMe 文档写入成功；
7. 文档链接和 Markdown 规范检查通过。

AskMe 不负责确认文件级模板、Schema、错误码、索引刷新、路由识别、迁移字段映射或脚本实现。这些内容由 Overall/Detail 在各自阶段确认。

门禁失败时，结果必须是 `clarifying` 或 `blocked`，并列出缺失项，不能为了让流程继续而自动补全结论。

## 12. 统一输出

每次调用都返回结构化结果，同时把完整文档落盘：

```json
{
  "phase": "askme",
  "status": "clarifying",
  "subject_type": "feature",
  "subject_id": "FT-xxx",
  "project_id": "PJ-001",
  "artifact": "docs/devflow/features/FT-xxx-name/FT-xxx-name-AskMe.md",
  "pending_decision_ids": ["D2"],
  "confirmed_decision_count": 3,
  "acceptance_criteria_count": 5,
  "blocking_items": [],
  "next_steps": ["继续确认 D2"]
}
```

当状态为 `completed` 时，`pending_decision_ids` 必须为空，
`next_steps` 应指向 `overall`。当状态为 `blocked` 或 `conflict` 时，
`blocking_items` 必须说明原因和恢复动作。

`subject_type`、`subject_id` 和 `project_id` 是所有命令输出的必填身份字段；
Project 输出时 `subject_type` 为 `project`，`subject_id` 为 `PJ-xxx`，
并且不输出仅适用于 Feature 的 `feature_id`。`artifact`、`next_steps` 和状态字段
必须与实际落盘结果一致，不能用 Markdown 正文中的名称替代机器状态。

## 13. 一次完整访谈示例

### 13.1 用户第一次输入

```text
给用户列表增加批量导出，手机上也要能操作。
```

### 13.2 Skill 的第一轮处理

Skill 先检查现有代码，发现：

- 已有用户列表页和单条导出入口；
- 现有权限只允许管理员导出；
- 没有批量导出接口；
- 项目默认工作流为 `standard`。

因此它不再询问“是否需要导出入口”，而是展示：

```text
D1：批量导出的权限是否沿用现有管理员权限？

推荐：沿用管理员权限，并在验收标准中明确非管理员不可见、不可调用。
依据：现有单条导出入口的权限检查。
```

用户确认后，Skill 保存：

```text
用户结论：沿用管理员权限。
验收标准：非管理员看不到批量导出入口；直接调用接口返回 403。
```

### 13.3 后续决策点

接下来可能依次确认：

1. 导出字段和筛选条件；
2. 最大数据量；
3. 同步下载还是异步任务；
4. 手机端的操作入口和结果查看方式；
5. 导出失败、取消和重复提交；
6. 验收中的性能、权限、可访问性和兼容性要求。

### 13.4 中断与恢复

如果用户在 D3 后关闭会话，再次输入“继续 FT-xxx”，Skill 应显示：

```text
已确认 D1、D2，当前从 D3“超过 10,000 条记录时的处理方式”继续。
```

它不应重新询问 D1，也不应依赖上一次聊天记录。

## 14. 与后续阶段的交接

AskMe 完成后交给 Overall 的不是一句“需求已确认”，而是一组结构化事实：

- 用户目标和目标用户；
- 已确认决策及用户理由；
- 验收标准汇总；
- 范围内和范围外；
- 假设、依赖和风险；
- UI 决策；
- L0 现状证据。

Overall 可以基于这些事实生成场景和总体方案，但不能重新解释已确认决策。发现需求不足或决策翻转时，应回到 AskMe 或进入 `sync`。

## 15. AskMe 行为契约

生成 Skill 的 AI 至少要实现以下具体行为，而不是只生成一个提问模板：

- 新建和恢复两条路径；
- 编号冲突检查；
- 风险档位判断和升级；
- L0 调研后再提问；
- 决策点依赖和分批提问；
- 模糊回答追问；
- 用户确认和验收标准绑定；
- 每轮原子落盘；
- `state.json` 驱动恢复；
- 已确认决策变更转 sync；
- 完成门禁和统一 JSON 输出。

## 16. Detail 待补项
